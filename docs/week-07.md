# Неделя 7 — простое распределение

## Как использовать
1. В /admin/accounts/user/ откройте сотрудника.
2. В блоке «Распределение лидов» выберите услуги, которые он умеет выполнять.
3. Включите «Принимает новые лиды» и задайте лимит активных лидов (по умолчанию 5).
4. Сотрудник также должен быть активным и иметь is_staff.
5. Создайте новый лид без ответственного с подходящей услугой.
6. На /kanban/ нажмите «Подобрать сотрудника».

Кнопка доступна для новых неназначенных лидов пользователю с правом leads.change_lead.
При успехе появится сотрудник, а карточка перейдёт в «Назначен».
Если никто не подходит, выводится причина и лид не изменяется.
Существующим сотрудникам доступность по умолчанию не включается; навыки тоже нужно указать.
При создании сотрудника стандартная форма сначала задаёт учётную запись; навыки настройте после сохранения.

## Правила
Услуга лида → сотрудники с нужным навыком → активные сотрудники, принимающие лиды →
загрузка меньше личного лимита → минимальная загрузка → назначение.

Загрузка — количество лидов сотрудника со статусами new, in_progress, assigned по всем услугам.
won и lost не учитываются. При равенстве выбирается меньший id сотрудника.
«Свободен» здесь означает «принимает лиды и ещё не достиг лимита», а не наличие окна в календаре.
Заказы пока не включены в подсчёт: у Order ещё нет статусов завершения.
Расстояние, адреса, рабочие смены и геолокация пока не учитываются.
Распределение запускается вручную кнопкой; при создании лида автоматически не срабатывает.

Лимит применяется именно к подбору: ручные назначения в админке могут его превысить.
Назначенного или закрытого лида алгоритм не переназначает и не открывает заново.
Если хотите повторно распределить лид, сначала осознанно очистите ответственного и верните статус «Новый» в админке.

## Данные
User.services — ManyToManyField: сотрудник умеет несколько услуг, одну услугу умеют несколько сотрудников.
Django создаёт промежуточную таблицу связей.
User.is_available — ручной флаг приёма новых лидов (по умолчанию False).
User.max_active_leads — лимит, по умолчанию 5, в формах минимум 1.

## API и алгоритм
POST /api/leads/<id>/assign/ с пустым JSON {}.
Сервер сам выбирает сотрудника; передать employee_id через этот API нельзя.
Требуются сессия, CSRF, права просмотра лидов/клиентов и изменения лида, is_staff.
Ответ 200 — обновлённая карточка с employee_id и employee_name.
409 — лид уже назначен/не новый или нет подходящих сотрудников; 404 — лид отсутствует.

backend/apps/leads/assignment.py содержит алгоритм отдельно от HTTP:
- transaction.atomic объединяет подбор и сохранение;
- select_for_update блокирует лид;
- подходящие сотрудники блокируются в порядке id;
- после получения блокировок считается загрузка;
- сотрудник и статус сохраняются вместе.

Блокировки PostgreSQL сериализуют одновременные запросы этого алгоритма для общих кандидатов.
Обычные ручные изменения через админку не используют этот протокол распределения.
SQLite-тесты проверяют правила, но не поведение блокировок PostgreSQL.

## Проверки
Прошли 34 Django-теста на SQLite и 8 браузерных сценариев, включая назначение через настоящий PostgreSQL.
Тестовые записи сквозных сценариев удалены.
Запуск:
~~~powershell
.\.venv\Scripts\python.exe backend/manage.py test apps.leads apps.orders --noinput
npm --prefix frontend run build
$env:RUN_POSTGRES_E2E = "1"
try {
    npm --prefix frontend test
} finally {
    Remove-Item Env:RUN_POSTGRES_E2E
}
~~~
Для Django-тестов на отдельной PostgreSQL-базе нужно CREATEDB; сквозной тест создаёт временные записи в уже настроенной базе.
