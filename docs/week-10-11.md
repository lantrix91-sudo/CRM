# Недели 10–11 — телефония и источники

## Универсальная телефония
Реализован адаптер входящих звонков, не привязанный к поставщику АТС.
АТС или промежуточный адаптер отправляет POST /api/telephony/incoming/:
~~~json
{"event_id": "pbx-call-0001", "phone": "+7 (700) 123-45-67"}
~~~
Если услуга известна, добавьте service_id — существующий ID услуги.
Заголовки: Content-Type: application/json и Authorization: Bearer ВАШ_СЕКРЕТ.
В .env задайте TELEPHONY_WEBHOOK_TOKEN длинным случайным секретом и перезапустите Django.
Без секрета доступ закрыт. Для внешней АТС потребуется доступный HTTPS-адрес CRM.
Реальная АТС пока не подключена; нужно настроить преобразование её событий в этот контракт.

Один event_id обозначает один входящий звонок. Повторы используют тот же ID.
201 — создан звонок; 200 — уже обработан; 400 — неверные данные; 403 — неверный секрет.
ID должен быть уникален среди всех подключённых линий/АТС: при необходимости добавляйте префикс провайдера.
Ответ содержит call_id, client_id, lead_id, needs_review и history_url.
Не передавайте в этот endpoint события окончания/записи разговора: здесь только начало входящего звонка.

## Поиск клиента
Пунктуация номера убирается. Начальная 8 у 11-значного номера заменяется на +7.
Остальные номера сравниваются по цифрам с префиксом +; нужны полные номера с кодом страны.
Это простая нормализация, не проверка реального существования номера.
Исходное поле phone сохранено, индексированное normalized_phone используется для поиска.
Существующие номера обработаны миграцией.
При изменении телефона через save/админку индекс обновляется; bulk_update/QuerySet.update обходят save,
поэтому при импорте требуется самостоятельно обновлять normalized_phone.

Если найден один клиент, новый лид относится к нему. Если никого — создаётся клиент с временным именем.
Если найдено несколько клиентов, CRM сохраняет звонок без выбора клиента и без лида:
оператор в /calls/ выбирает «Разобрать звонок» и указывает правильного клиента в админке.
При сохранении появляется лид. Для такой операции нужны право изменения звонков, создания лида и просмотра клиентов.

Каждый новый звонок создаёт отдельный лид с источником «Телефон». Повтор того же event_id не создаёт дубль.
Услуга может быть пустой: выберите её в админке перед распределением или созданием заказа.
Оператору звонки автоматически не распределяются.

## Интерфейс
- /calls/ — журнал входящих звонков, по 30 на страницу.
- /clients/<id>/history/ — клиент и последние 50 обращений, заказов и звонков каждого типа.
- /analytics/ — лиды за сегодня по источникам.
Страницы доступны после входа сотрудника. Новые звонки появляются после обновления страницы;
автоматическое всплывающее окно и push-события пока не добавлены.

История требует customers.view_client, leads.view_lead, orders.view_order, leads.view_incomingcall и is_staff.
Журнал — leads.view_incomingcall и customers.view_client.
Аналитика — отдельное право leads.view_analytics. Суперпользователь имеет доступ сразу.

## Пример тестового события
Запустите Django, заполните секрет в .env, затем из корня:
~~~powershell
.\.venv\Scripts\python.exe docs/send-test-call.py --event-id demo-call-001 --phone "+7 (700) 123-45-67"
~~~
Повторите ту же команду: вернётся тот же звонок и лид.
Для нового звонка используйте другой event-id.
Скрипт создаёт настоящие тестовые записи в локальной CRM; автоматического удаления нет.
Не используйте чужие реальные номера для учебных событий.
Секрет читается из .env, не выводится и не передаётся аргументом командной строки.

## Источники
В форме лида доступны OLX, Google, Instagram, Telegram, Телефон.
Старые нестандартные значения сохранены и тоже доступны в списке.
Это классификация лидов; интеграции с OLX, Google и Instagram пока не добавлены.
Telegram-уведомление сотруднику не меняет источник клиента.

Отчёт считает created_at в пределах текущих суток по TIME_ZONE CRM (Asia/Qyzylorda).
Включаются все созданные сегодня лиды независимо от текущего статуса, в том числе конвертированные.
OLX и olx с пробелами объединяются. Нестандартные источники идут в «Другие», пустые — «Не указан».
Нулевые строки показаны, итог равен сумме всех строк.
Дата отчёта относится к моменту поступления события в CRM, а не ко времени звонка на стороне АТС.

## Код и проверки
- customers/phones.py — нормализация.
- leads/telephony.py — защита webhook, валидация, идемпотентное создание.
- leads/reports.py — история, журнал и агрегирование.
- leads/forms.py — список источников с сохранением старых значений.
- leads/test_telephony.py — проверочные сценарии.
- docs/send-test-call.py — тестовый отправитель.

Миграции применены; 63 Django-теста прошли на SQLite.
PostgreSQL блокирует обработку повторного события и параллельное создание клиента по одному номеру
в рамках этого webhook; ручное создание клиентов в админке не использует такую блокировку.
Несколько клиентов с общим номером по-прежнему допустимы.
